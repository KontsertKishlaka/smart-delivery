# Архитектура проекта SmartDelivery

## 1. Общие сведения

Тут описана архитектура системы **SmartDelivery**.

Система построена по принципу микросервисной архитектуры (MSA) и объединяет клиентов, операторов колл-центра, курьеров и бухгалтерию (1С) в едином пространстве.

Все компоненты упакованы в Docker-контейнеры и управляются единым файлом `docker-compose.yml`. Взаимодействие между сервисами осуществляется синхронно (REST, gRPC) и асинхронно (RabbitMQ). В качестве основных хранилищ используются PostgreSQL и Redis.

## 3. Структура развертывания

Все сервисы и инфраструктурные компоненты запускаются на одном Docker-хосте через `docker-compose`. Для продакшн-окружения предполагается вынос stateful-сервисов (PostgreSQL, RabbitMQ, Redis) в отказоустойчивые кластеры.

**Основные группы компонентов:**

- **Клиентские интерфейсы:** Telegram (для конечных клиентов), Next.js-приложение (панель оператора и мобильная версия курьера);
- **Точка входа:** API Gateway на FastAPI;
- **Бизнес-микросервисы:** Order, Restaurant, Courier, Geo, Notification, Integration-1C, LLM Agent;
- **Инфраструктура:** RabbitMQ, Redis, PostgreSQL.

## 4. Детальное описание сервисов

### **4.1. Frontend (Next.js)**

**Назначение:** веб-интерфейс для операторов/менеджеров и курьеров.

**Технологии:** Next.js 14+ (TypeScript), компонент Яндекс.Карты для отображения карты.

**Взаимодействие:**

- Оператор и курьер обращаются к Frontend по HTTPS;
- Frontend отправляет REST-запросы к API Gateway (Gateway), который проксирует их в соответствующие сервисы;
- Картографический компонент загружает JS API Яндекса напрямую из браузера пользователя.

**Особенности:**

- Реализует две ролевые зоны: панель оператора (таблица заказов, карта с курьерами, справочники) и упрощённый мобильный вид для курьера (текущий заказ, маршрут, кнопки смены статуса);
- Не сохраняет состояние, является тонким клиентом.

### **4.2. API Gateway (FastAPI)**

**Назначение:** единая точка входа для всех бэкенд-запросов от Frontend и Telegram-бота.

**Технологии:** Python 3.11+, FastAPI, Pydantic.

**Взаимодействие:**

- Принимает REST-запросы от Frontend и сервиса Telegram Bot;
- Маршрутизирует запросы к целевым бизнес-сервисам через внутренние REST-вызовы;
- Не содержит бизнес-логики;
- Обеспечивает аутентификацию (JWT-проверка) и проксирование.

**Особенности:**

- Реализует сквозную проверку Bearer token для всех защищённых эндпоинтов;
- Конфигурация конечных точек сервисов задаётся через переменные окружения.

### **4.3. Telegram Bot (python-telegram-bot / aiogram)**

**Назначение:** клиентский канал для конечных пользователей через Telegram.

**Технологии:** асинхронная библиотека python-telegram-bot или aiogram.

**Взаимодействие:**

- Получает обновления от Telegram Bot API через webhook (рекомендуется для разработки с ngrok) **ИЛИ** polling;
- Команды бота (/start, /menu, /order, /status) преобразуются в REST-запросы к **API Gateway**.

**Особенности:**

- Обрабатывает регистрацию клиента по номеру телефона, выбор ресторана/меню, сбор корзины, отправку геолокации;
- Сообщения о статусах заказа и ответы LLM-агента доставляются через сервис **Notification**.

### **4.4. Order Service (order-service)**

**Назначение:** управление жизненным циклом заказов.

**Технологии:** FastAPI, SQLAlchemy async, Alembic.

**Основные функции:**

- Создание заказа, хранение состава, адресов, статусов;
- Статусная машина заказа: Принят → Готовится → Передан курьеру → В пути → Доставлен;
- Публикация событий в **RabbitMQ** при создании и смене статуса;
- Запрос маршрута и поиск ближайших курьеров через gRPC-вызовы к **Geo Service**.

**Хранение:** PostgreSQL - таблицы заказов, позиций, статусов.

**Ключевые события:**

- `order.created`
- `order.status_changed`
- `courier.assigned`
- `order.completed`

### **4.5. Restaurant Service (restaurant-service)**

**Назначение:** CRUD-управление ресторанами-партнёрами и их меню.

**Технологии:** FastAPI, SQLAlchemy async.

**Функции:**

- Добавление/редактирование/удаление ресторанов;
- Управление меню: блюда, цены, фото (ссылки);
- Предоставление списков для клиентских интерфейсов.

**Хранение:** PostgreSQL - таблицы ресторанов, меню, категорий.

### **4.6. Courier Service (courier-service)**

**Назначение:** управление курьерами и их трекинг.

**Технологии:** FastAPI, SQLAlchemy async.

**Функции:**

- Регистрация/авторизация курьеров;
- Принятие/отклонение заказа;
- Просмотр текущего заказа, адресов, контактов;
- Смена статусов: "забрал заказ", "в пути", "доставлен" (с возможностью прикрепить фото);
- Фоновая отправка текущих координат (каждые 10 секунд через gRPC в **Geo Service**);
- Публикация событий смены статуса в **RabbitMQ**.

**Хранение:** PostgreSQL - профили курьеров, смены, статусы.

### **4.7. Geo Service (geo-service)**

**Назначение:** геокодирование, построение маршрутов и поиск ближайших курьеров. Единственный сервис, предоставляющий API исключительно по протоколу gRPC.

**Технологии:** Python, grpcio, grpcio-tools, Redis.

**Реализуемые gRPC-методы:**

- GetRoute - построение маршрута от курьера к ресторану и до клиента с учётом пробок (через Яндекс.Карты HTTP API);
- Geocode - прямое и обратное геокодирование адресов;
- (внутренний) поиск ближайших курьеров: использует Redis GEORADIUS.

**Хранение и кэширование:**

- Координаты курьеров хранятся в **Redis** с помощью GEOADD;
- Одинаковые пары адресов кэшируются в **Redis** на 30 минут для снижения нагрузки на внешний API.

**Внешние зависимости:** Яндекс.Карты API (HTTP).

**ВАЖНО!** Ключ API от Яндекс.Карты хранится в переменных окружения.

### **4.8. Notification Service (notification-service)**

**Назначение:** формирование и отправка уведомлений клиентам и курьерам через Telegram.

**Технологии:** FastAPI, python-telegram-bot.

**Взаимодействие:**

- Подписан на очередь событий **RabbitMQ**: `order.created`, `order.status_changed`, `courier.assigned`;
- При получении события извлекает идентификатор чата и отправляет сообщение через Telegram Bot API.

**Особенности:**

- Шаблоны сообщений настраиваются в конфигурации;
- При **недоступности RabbitMQ** сообщения **не теряются** (durable queue).

### **4.9. Integration-1C (integration-1c)**

**Назначение:** выгрузка закрытых заказов в **бухгалтерскую систему 1С**.

**Технологии:** FastAPI, HTTP-клиент.

**Взаимодействие:**

- Потребляет события `order.completed` из **RabbitMQ**;
- Формирует JSON-пакет в формате, соответствующем типовому документу "Реализация товаров";
- Отправляет пакет на REST-эндпоинт учебного стенда 1С с аутентификацией **HTTP Basic Auth**;
- При **недоступности 1С** повторяет попытки с экспоненциальной задержкой;
- Ведёт лог успешных и неуспешных отправок.

**Альтернативный режим:** ручная выгрузка через кнопку в панели оператора (через вызов Gateway -> сервис).

### **4.10. LLM Agent (llm-agent)**

**Назначение:** интеллектуальная обработка сообщений клиентов: классификация заказов, автоответы на типовые вопросы, модерация отзывов.

**Технологии:** FastAPI, подключение к бесплатной LLM через Ollama (локально) или OpenRouter API.

**Функции:**

- Классификация входящих заказов из Telegram по ***типу кухни*** и ***срочности*** на основе текста;
- Автоматический ответ на частые вопросы ("где мой заказ?", "сколько ждать?");
- При неуверенности модели - перевод запроса в очередь "на оператора";
- Модерация новых отзывов (событие review.created);
- Кэширование ответов в **Redis** (ключ = хэш промпта, TTL 1 час).

**Внешний вызов:** REST к Ollama (локальная модель llama3.2 или gemma2:2b) или к OpenRouter API.

**ВАЖНО!** Ключ API провайдера задаётся через переменные окружения.

### **4.11. Инфраструктурные сервисы**

|**Сервис**|**Назначение**|
| :-: | :-: |
|**PostgreSQL**|Основное реляционное хранилище данных. Поддерживает миграции через Alembic.|
|**RabbitMQ**|Асинхронная шина сообщений. Обменник smartdelivery.events. Гарантирует доставку событий, включая *retry* и *dead-letter* механизмы.|
|**Redis**|Используется для: хранения гео-координат курьеров (GEOADD), кэширования маршрутов и ответов LLM, сессий, временных данных.|

**ВАЖНО!** В dev-окружении **PostgreSQL** может заменяться на **SQLite** для упрощения разработки.

## 5. Коммуникационные протоколы и потоки данных

### **5.1. Синхронные вызовы**

- **Frontend -> Gateway:** REST/HTTPS (JSON). Все запросы аутентифицируются Bearer JWT;
- **Gateway → Бизнес-сервисы:** REST/HTTPS (внутренняя сеть Docker). Маршрутизация на основе URL;
- **Geo Service:** предоставляет только **gRPC** API для низкой задержки и строгих контрактов. Используется сервисами **Order** и **Courier**;
- **Geo Service → Яндекс.Карты:** HTTPS (серверный HTTP API);
- **LLM Agent → LLM-провайдер:** HTTPS (REST);
- **Integration-1C → 1С:** HTTPS с **HTTP Basic Auth**.

### **5.2. Асинхронная шина (RabbitMQ)**

Основной обменник: smartdelivery.events (topic exchange).

|**Событие**|**Публикует (producer)**|**Потребители (consumer)**|**Назначение**|
| :-: | :-: | :-: | :-: |
|`order.created`|Order Service|Notification, (бот)|Уведомление клиенту, курьерам (поиск назначения)|
|`order.status_changed`|Order / Courier|Notification, Order (история)|Обновление статуса в Telegram и панели оператора|
|`courier.assigned`|Order Service|Notification|Уведомление назначенному курьеру|
|`order.completed`|Order Service|Integration-1C|Запуск выгрузки в 1С|
|`review.created`|(будущий сервис)|LLM Agent|Автоматическая модерация отзыва|

**ВАЖНО!** Очереди - *durable*, сообщения - *персистентные*.

**ВАЖНО!** При **сбоях RabbitMQ** предусмотрен механизм *dead-letter* и механизм *повторных попыток*.

## 6. Безопасность

- **Аутентификация:**
  - **Клиент** и **Курьер** - по номеру телефона и коду;
  - **Оператор** - email/пароль с выдачей JWT.
- **Авторизация:** ролевая модель (client, courier, operator, admin), enforced на Gateway;
- **Конфиденциальность данных:**
  - адреса и телефоны клиентов не логируются в открытом виде;
  - чувствительные данные не покидают периметр без необходимости.
- **Внешние API:** ключи Яндекса, LLM-провайдера, 1С хранятся **ИСКЛЮЧИТЕЛЬНО** в переменных окружения Docker-контейнеров.

## 7. Масштабируемость и отказоустойчивость

- Каждый бизнес-сервис - независимый Docker-контейнер, допускающий горизонтальное масштабирование;
- При падении **Geo Service** создание заказа не блокируется - маршрут рассчитывается асинхронно с fallback-ом на прямой геометрический расчёт;
- **RabbitMQ** гарантирует доставку событий даже при временной недоступности потребителей;
- Выгрузка в 1С при недоступности шлюза откладывается с экспоненциальной задержкой;
- Кэширование в **Redis** снижает нагрузку на **внешние API** и **LLM**.
