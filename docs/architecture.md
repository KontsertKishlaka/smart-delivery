# Архитектура проекта

## 1. Общие сведения

Проект построен по принципам MSA. Каждый сервис выполняет свою бизнес-функцию и общается с другими синхронно через REST API (HTTP). Все сервисы контейнеризированы с помощью Docker и управляются через `docker-compose.yml`. В качестве основной БД используется PostgreSQL (одна БД, но с изолированными схемами). Логи пишутся в stdout в формате JSON.

## 3. Структура развертывания

Все сервисы и инфраструктурные компоненты запускаются на одном Docker-хосте с помощью `docker-compose`.

**Группы компонентов:**

- **Клиентские интерфейсы**:
  - Telegram-бот - взаимодействие с клиентами;
  - Веб-панель оператора (Vue SPA) - для операторов.
- **Точка входа (API Gateway)**:
  - Реализован на Go. Принимает все REST-запросы от фронтенда (админки) и бота, проксирует в соответствующие бизнес-сервисы, проверяет аутентификацию оператора (JWT не используется - полагается на cookie-сессии; gateway проверяет наличие сессии через сервис операторов).
- **Бизнес-микросервисы**:
  - `order-service` (Go) - управление заказами, статусная машина, хранение заказов;
  - `restaurant-service` (Python) - CRUD ресторанов и меню;
  - `notification-service` (Python) - отправка уведомлений в Telegram;
  - `integration-1c` (Python) - выгрузка закрытых заказов в 1С;
  - `telegram-bot` (Python) - обработка диалога с клиентом, вызов API Gateway.
- **Инфраструктура**:
  - PostgreSQL (общая БД, схемы: `order_schema`, `restaurant_schema`, `operator_schema`, `notification_logs`, `export_logs`).
- **Внешние системы**:
  - Telegram Bot API;
  - Учебный стенд 1С (HTTP-сервис, принимающий JSON-пакеты);
  - OpenStreetMap (Leaflet.js) - используется только на фронтенде для отображения статических меток.

## 4. Детальное описание сервисов

### 4.1. Frontend (Веб-панель оператора)

- **Назначение**: веб-интерфейс для операторов;
- **Технологии**: Vue 3, Vuetify, Vue Router, Vuex 4, Vue i18n, Axios;
- **Взаимодействие**: отправляет REST-запросы к API Gateway (Axios);
- **Особенности**: SPA, поддержка двух языков, статические карты OpenStreetMap (через Leaflet).

### 4.2. API Gateway (Go)

- **Назначение**: единая точка входа для всех клиентских запросов;
- **Технологии**: Go (net/http), reverse proxy;
- **Взаимодействие**: принимает REST-запросы от админки и бота, проксирует в соответствующие сервисы. Проверяет cookie сессии оператора (если запрос от админки);
- **Особенности**: не содержит бизнес-логики, конфигурация маршрутов через переменные окружения.

### 4.3. Telegram Bot (Python)

- **Назначение**: обработка команд и сообщений от клиентов;
- **Технологии**: aiogram, FastAPI (для webhook);
- **Взаимодействие**: получает обновления от Telegram Bot API (webhook), преобразует команды в REST-запросы к Gateway, отправляет ответы клиенту через Telegram API;
- **Особенности**: не хранит состояние диалога (легковесный).

### 4.4. Order Service (Go)

- **Назначение**: управление заказами;
- **Технологии**: Go, PostgreSQL driver;
- **Основные функции**:
  - Создание заказа (состав, адрес, статус);
  - Обновление статуса заказа;
  - Получение списка заказов с фильтрацией;
  - Получение деталей заказа;
  - Генерация отчетов (сумма заказов за период).
- **Хранение**: схема `order_schema` в PostgreSQL.

### 4.5. Restaurant Service (Python)

- **Назначение**: CRUD ресторанов и меню;
- **Технологии**: FastAPI, SQLAlchemy async, Alembic;
- **Основные функции**:
  - Добавление/редактирование/удаление ресторанов;
  - Управление блюдами (название, цена, ссылка на фото);
  - Предоставление списков для клиентских интерфейсов.
- **Хранение**: схема `restaurant_schema` в PostgreSQL.

### 4.6. Notification Service (Python)

- **Назначение**: отправка уведомлений клиентам;
- **Технологии**: FastAPI, HTTP-клиент;
- **Взаимодействие**: вызывается синхронно из Order Service (при изменении статуса) или через Gateway (например, при создании заказа). Формирует сообщение и отправляет запрос к Telegram Bot API;
- **Хранение**: опционально логирует отправленные уведомления в схеме `notification_logs`.

### 4.7. Integration-1C (Python)

- **Назначение**: выгрузка завершенных заказов в учебный стенд 1С;
- **Технологии**: FastAPI, HTTP-клиент;
- **Функции**:
  - По запросу (автоматически по накоплению или вручную) собирает заказы со статусом "Доставлен";
  - Формирует JSON по согласованной с 1С структуре;
  - Отправляет POST-запрос на эндпоинт учебного стенда 1С с Basic Auth;
  - Логирует результат в таблицу `export_logs`.
- **Хранение**: схема `export_logs` в PostgreSQL.

## 5. Коммуникационные протоколы и потоки данных

Все взаимодействия синхронные, только REST/HTTP.

- **Frontend => Gateway**: REST/HTTPS (JSON). Аутентификация через cookie-сессию;
- **Gateway => Бизнес-сервисы**: REST/HTTP (внутренняя сеть Docker). Дополнительная аутентификация не требуется (только для вызова извне);
- **Bot => Gateway**: REST/HTTPS. Клиент идентифицируется по номеру телефона (передается в теле запроса);
- **Notification Service => Telegram Bot API**: REST/HTTPS с токеном бота;
- **Integration-1C => Учебный стенд 1С**: REST/HTTPS с Basic Auth;
- **Frontend => OpenStreetMap (JS)**: прямой вызов из браузера (CORS не требуется).

## 6. Нефункциональные требования

### 6.1. Безопасность

- Пароли операторов хранятся в БД в хешированном виде (bcrypt);
- Сессии операторов реализованы через cookie с серверной памятью (или использовать `sessions` в FastAPI);
- Доступ к Gateway извне только через порт 8000 (или 80). Внутренние порты сервисов не публикуются;
- Все секреты (токен Telegram бота, пароль БД, Basic Auth для 1С) - в `.env` файле.

### 6.2. Масштабируемость и отказоустойчивость

- `healthcheck` для каждого сервиса;
- Таймауты на все внешние вызовы (5 секунд).

### 6.3. Наблюдаемость

- Логирование: каждый сервис пишет в stdout структурированные логи (JSON) с уровнем INFO/ERROR;
- Нет метрик и трейсинга.

### 6.4. Версионирование API

- Все публичные эндпоинты Gateway имеют префикс `/api/v1/`.
