# Техническое задание на разработку системы "SmartDelivery"

## 1. Общие сведения

### 1.1. Наименование системы

Полное: **SmartDelivery - система управления доставкой готовой еды из ресторанов**
Краткое: **smart-delivery**

### 1.2. Заказчик

**ООО "ТехноФуд"** - оператор агрегационной платформы доставки еды.

### 1.3. Назначение системы

SmartDelivery предназначена для автоматизации процессов приёма, обработки и исполнения заказов на доставку готовой еды из ресторанов. Система объединяет клиентов, операторов колл-центра, курьеров и бухгалтерию (1С) в единое информационное пространство.

### 1.4. Цели создания системы

- Уменьшить время обработки заказа и повысить точность маршрутизации;
- Обеспечить многоканальный приём заказов (Telegram-бот, панель оператора);
- Интегрировать геоинформационные сервисы для автоматического построения маршрутов и отслеживания курьеров;
- Снизить нагрузку на операторов за счёт внедрения LLM-агента для классификации и ответов на типовые вопросы;
- Автоматизировать передачу закрытых заказов в бухгалтерскую систему (1С);
- Создать масштабируемую MSA, которая интегрирована с gRPC, RabbitMQ и Redis.

## 2. Область применения

Система охватывает бизнес-процессы:

- Регистрация и управление ресторанами-партнёрами и их меню;
- Приём заказов от ***конечных клиентов*** через ***Telegram-бота*** и через ***веб-интерфейс оператора***;
- Назначение заказов на ближайших свободных курьеров;
- Построение и мониторинг маршрутов доставки с использованием **Яндекс.Карты**;
- Уведомление клиентов и курьеров об изменении статусов;
- Формирование отчётных документов и выгрузка завершённых заказов в внешнюю систему **1С**;
- Модерация отзывов и классификация заказов с привлечением бесплатных **LLM**.

**ВАЖНО!** Система не предназначена для прямого взаимодействия с конечными клиентами через мобильное приложение (только Telegram и веб-интерфейс для операторов/менеджеров).

## 4. Нефункциональные требования

### 4.1. Архитектура

**ВАЖНО!** Подробная архитектура проекта уже описана в документе [Архитектура проекта](architecture.md).

Система реализуется в виде набора микросервисов, общающихся синхронно (REST, gRPC) и асинхронно (RabbitMQ). Каждый сервис упаковывается в Docker-контейнер.

**Основные сервисы:**

- `gateway` - FastAPI, единая точка входа для фронтенда (Next.js) и Telegram бота, проксирует запросы;
- `order-service` - управление заказами, статусная машина;
- `restaurant-service` - CRUD ресторанов и меню;
- `courier-service` - управление курьерами, трекинг;
- `geo-service` - взаимодействие с Яндекс.Карты, gRPC-сервер для расчёта маршрутов;
- `notification-service` - формирование и отправка уведомлений (Telegram, push-уведомления);
- `integration-1c` - выгрузка данных в 1С;
- `llm-agent` - обработка сообщений через LLM;
- `python-telegram-bot` - адаптер для Telegram Bot (внутри gateway).

**Коммуникация:**

- Синхронные запросы между сервисами (за исключением `geo-service`) - REST с JSON;
- Запросы к `geo-service` - **gRPC** (proto-контракты на расчёт маршрута и геокодирование);
- Асинхронная шина - **RabbitMQ** (обменник smartdelivery.events).

### 4.2. Стек технологий

- **Backend:** Python 3.11+, FastAPI, SQLAlchemy (async), Alembic, Pydantic;
- **Frontend:** Next.js 14+ (TypeScript), связь с backend через REST API;
- **gRPC:** grpcio, grpcio-tools, сервис `geo-service` предоставляет методы `GetRoute`, `Geocode`;
- **RabbitMQ:** aio_pika для асинхронных продюсеров/консюмеров;
- **Redis:** redis-py для кэширования, хранения координат (GEO), сессий, кэша LLM;
- **БД:** SQLite для local/dev окружения; PostgreSQL 15 для production-подобного (можно поднимать вместе в docker-compose);
- **ORM:** SQLAlchemy 2.0 async с миграциями Alembic;
- **Контейнеризация:** Docker, docker-compose (один файл `docker-compose.yml` для локального запуска всей системы);
- **API-документация:** SwaggerUI из коробки FastAPI + экспорт в Confluence;
- **Техническая документация:** ведётся в Confluence (описание архитектуры, контракты API, ER-диаграммы);
- **Система управления проектом:** Jira;
- **Контроль версий:** Git, GitHub;
- **ОС разработки:** Windows 11, но весь инструментарий должен работать в Docker (Linux-контейнеры).

### 4.3. Производительность и масштабируемость

- Время отклика API (REST) - не более 300 мс для 95% запросов (без учёта внешних интеграций);
- gRPC-запросы к `geo-service` - не более 500 мс;
- Система должна выдерживать до 50 одновременных активных заказов;
- Кэширование маршрутов: одинаковые пары адресов кэшируются в Redis на 30 минут.

### 4.4. Безопасность

- Аутентификация клиентов и курьеров - по номеру телефона + код (имитация), для операторов - email/пароль с JWT;
- Все эндпоинты (кроме регистрации и входа) требуют **Bearer token**;
- Ролевая модель: **client**, **courier**, **operator**, **admin** (RBAC);
- Данные клиентов (адреса, телефоны) не должны логироваться в открытом виде;
- Внешние интеграции (Яндекс.Карты, 1С, LLM) обязаны использовать переменные окружения для API-ключей.

### 4.5. Надёжность и отказоустойчивость

- При недоступности RabbitMQ сообщения должны сохраняться и обрабатываться после восстановления (retry + dead-letter);
- Если 1С недоступна, выгрузка откладывается (повторы с экспоненциальной задержкой);
- Падение geo-service не должно блокировать создание заказа - маршрут рассчитывается асинхронно с фолбэком на прямую геометрию.

## 5. Интеграции

### 5.1. Яндекс.Карты

Используется JavaScript API для отображения карты на фронтенде и HTTP/JS API для геокодирования и маршрутов.

В рамках `geo-service` реализуется серверный доступ к HTTP API Яндекс.Карты (геокодер, маршрутизатор) с кэшированием.

**ВАЖНО!** API-ключ хранится в переменных окружения.

**Требования:**

- Отображение карты в панели оператора и в интерфейсе курьера (через компонент Яндекс.Карты в Next.js);
- Получение адреса по координатам и наоборот;
- Построение цветной линии маршрута на карте.

### 5.2. Telegram Bot

- Библиотека python-telegram-bot или aiogram (асинхронная);
- Бот должен поддерживать команды /start, /menu, /order, /status;
- Webhook-режим (туннель ngrok для локальной разработки) или polling.

### 5.3. 1С (базовая интеграция)

- REST-эндпоинт на стороне 1С (через отдельный микросервис);
- Формат обмена: JSON, структура соответствует типовому документу "Реализация товаров";
- Отправка происходит по протоколу **HTTP Basic Auth**.

### 5.4. LLM (бесплатная модель)

- Хорошие варианты:
  - локальный Ollama с моделью `llama3.2` или `gemma2:2b`;
  - провайдер [OpenRouter](https://openrouter.ai) с бесплатными лимитами.
- Обращение к LLM происходит через REST API из сервиса llm-agent;
- Промпты шаблонизированы для классификации и ответов;
- Ответ кэшируется в Redis (ключ = хэш промпта) на 1 час для идентичных запросов.

## 8. Критерии приёмки

- Через Telegram-бота можно заказать еду, получить подтверждение и отслеживать статус;
- Оператор видит заказ в панели, может изменить статус, видит курьеров на карте;
- Курьер получает уведомление о новом заказе, может его принять, видит маршрут на карте и меняет статусы;
- При завершении заказа данные автоматически уходят в 1С (+ видно в логах);
- Все сервисы взаимодействуют: RabbitMQ передаёт события, gRPC считает маршрут, Redis хранит координаты и кэш;
- Документация в Confluence + [README.md](../README.md) содержит все диаграммы, API-описание и инструкцию по запуску (`docker-compose up`);
- Код выложен на GitHub с историей коммитов, настроена релизная ветка `main`.
